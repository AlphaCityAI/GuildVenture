# GuildVenture optimization review

Reviewed August 29, 2026 against commit `2451f1485e9934efca7ff3d4d46f606e53554559`.

> Historical audit of the base revision. Implementation and verification are
> documented in [the implementation plan](../IMPLEMENTATION_PLAN.md) and
> [README](../README.md). Findings below describe the code before those fixes.

The highest-return work is to make the existing game rules, multiplayer flow, and rewards dependable, then remove AI generation from the critical interaction path. This is an audit, not an application rewrite. No application source, dependencies, deployment, or production data were changed.

**Scope and confidence.** I read all eight application Python modules (2,969 lines), the dependency and hosting configuration, project notes, victory specification, and the schemas of the three legacy saved games. I also examined the checked-in error logs with sensitive values withheld. The content includes seven factions, 21 faction abilities, seven boss archetypes, nine locations, and 35 item ability templates.

Twenty-two isolated reproductions confirmed existing defects using the original function bodies and in-memory substitutes for Telegram, OpenAI, and PostgreSQL. All eight application modules compile. The reproduction script deliberately asserts the current defective behavior: a passing reproduction is evidence of the defect, not evidence of a fix.

No live bot session, production database, API billing, deployed environment variables, or measured production latency was inspected. Deployment may override the model defaults. Production frequency and exact player impact require telemetry or staging validation.

**What is already useful.** Static ability/item/boss data gives the project a foundation for deterministic combat. PostgreSQL queries use parameters, and a connection pool is already present. Leaderboard sorting and limiting already happen in the database. Narrative history is bounded. Image-generation failure already has a text fallback. Preserve these choices while fixing incomplete integrations.

**Priority guide.** P1 means fix before broader playtesting or growth; P2 means address in the next improvement cycle; P3 means a later product opportunity. Effort is relative: S is a localized change, M touches several flows, L changes a subsystem. Estimates include focused verification and are not delivery commitments.

**AI reliability and a dated dependency risk.** Defaults are `gpt-4-turbo` and `gpt-image-1`; the committed SDK is OpenAI 1.77.0. Official documentation currently lists both defaults for shutdown on **October 23, 2026**. Check deployed overrides, choose supported replacements, and test request parameters, schema support, narrative quality, latency, and fallback behavior before switching. This is a required maintenance track, not a reason to change models blindly. [Defaults](https://github.com/drjnolen/GuildVenture/blob/2451f1485e9934efca7ff3d4d46f606e53554559/game_constants.py#L14), [OpenAI deprecations](https://developers.openai.com/api/docs/deprecations#2026-04-22-legacy-gpt-model-snapshots).

The application uses JSON mode, not a validated schema. JSON mode does not guarantee field types, permitted targets, or numeric ranges. Introduce local response models now and use Structured Outputs on a compatible replacement model; continue validating domain constraints even with schema adherence. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Boss retaliation is needlessly model-authoritative: the chosen ability already contains damage and target values, yet the app asks the model to return the damage map. Environmental retaliation does not even provide player IDs, making single-target output unreliable. Compute damage, healing, targets, modifiers, and deaths in Python; ask the model only to describe the resolved event. For campaign free text, keep interpretation separate from authoritative state transitions. [Boss prompt](https://github.com/drjnolen/GuildVenture/blob/2451f1485e9934efca7ff3d4d46f606e53554559/prompts.py#L35), [environment prompt](https://github.com/drjnolen/GuildVenture/blob/2451f1485e9934efca7ff3d4d46f606e53554559/prompts.py#L65).

The historical image 400 error cannot be diagnosed from the committed logs alone. The configured medium, 1024×1024 combination is documented for GPT Image 1; I would not call those parameters the confirmed cause. Capture sanitized provider error codes and request IDs, and verify account access/configuration in staging. [Image implementation](https://github.com/drjnolen/GuildVenture/blob/2451f1485e9934efca7ff3d4d46f606e53554559/main.py#L78), [model documentation](https://developers.openai.com/api/docs/models/gpt-image-1).

Do not solve P01 by setting unrestricted concurrency. Today the serial dispatcher limits ordinary same-process update races. The persistence layer still performs read-modify-write without row versions, and the saved boolean lock is not an atomic compare-and-set. Background jobs, multiple workers, or concurrent updates would expose lost updates in both per-chat state and globally shared profiles. Prefer short transactions or versioned writes; do not hold a database connection throughout an AI request. [State writes](https://github.com/drjnolen/GuildVenture/blob/2451f1485e9934efca7ff3d4d46f606e53554559/database.py#L97), [profile writes](https://github.com/drjnolen/GuildVenture/blob/2451f1485e9934efca7ff3d4d46f606e53554559/database.py#L130).

**Suggested implementation sequence and acceptance criteria.**

1. **Protect state and progress.** Implement D01–D05 and D13/D16, establish actor/run/turn IDs, and add persistence contracts. Acceptance: repeated/stale/unauthorized callbacks have no side effects; an outage cannot silently create a replacement profile; each reward/XP event is recorded once and can be delivered again safely.
2. **Restore the gameplay contract.** Fix lobby/join, combat traits, mappings, roll buffs, environment deaths, and rarity/bank math. Acceptance: two or more players can form a party; every declared effect type has a working resolver; all six rarity tiers have explicitly tested odds; numeric UI descriptions come from the same rules.
3. **Complete existing modes.** Implement campaign completion, ally persistence, loadout timing, and co-op reward claims. Acceptance: a campaign can reach a reward screen; an ally survives a restart; each eligible player can claim without resetting another player's claim.
4. **Improve responsiveness with safeguards.** Add bounded cross-chat concurrency, per-session sequencing, durable media jobs, budget controls, and compact messages. Acceptance: a stalled generation in chat A does not stop chat B; same-chat actions remain ordered; fallback/delivery retries never duplicate grants. Measure latency before and after.
5. **Ship experience improvements and progression.** Start with onboarding, /status, inventory comparison, and the existing victory recap proposal. Then evaluate deeper balance/crafting/challenge features using actual completion and retention data.
6. **Run the model migration as a parallel maintenance track before October 23, 2026.** Verify production overrides, choose supported models, update parameters and schema handling, and stage comparison fixtures. Do not defer this until the entire feature roadmap is complete.
